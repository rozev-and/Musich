# MUSICH — синхронизация устройств

Договор о том, как устройства MUSICH живут сами по себе и сходятся вместе. Утверждён как основа
2026-11-04. Сделан этап 1 (журнал на сервере, см. «Как сделано»); остальное — впереди. Когда все этапы будут сделаны, он заменит раздел «Модель данных
и синхронизации» в [`API.md`](API.md), где сервер — единственный источник правды. Менять договор —
только здесь.

## Принципы

1. **Каждое устройство — полноценный MUSICH.** ПК, сервер, телефон: у каждого своя база и свои
   файлы, каждое работает без остальных — слушать, лайкать, править, собирать плейлисты.
   Сервер — просто устройство, которое всегда включено.
2. **Правда — журнал событий.** Любое изменение — событие. Состояние библиотеки на устройстве —
   это все известные ему события, применённые по порядку. Устройства обмениваются событиями,
   которых у другого нет.
3. **Знают все обо всём, файлы — по выбору.** Список треков, лайки, плейлисты, правки, история
   есть на каждом устройстве целиком. Сами файлы устройство держит по своей политике.
4. **Синхронизация никогда не встаёт.** Спорное решается временным правилом, а человек
   пересматривает его на странице «Конфликты», когда удобно.
5. **Ничего не теряется молча.** Удаление из библиотеки — через корзину; последнюю копию файла
   убрать нельзя; перезаписанная версия файла хранится, пока конфликт не решён.

## Устройства (узлы)

- **id узла** — случайная строка, создаётся при первом запуске MUSICH на устройстве и не меняется.
  Имя («Домашний ПК», «Телефон») и тип (`desktop` / `laptop` / `phone` / `server`) — свойства узла.
- **Связь.** Узел с постоянным адресом (сервер, ПК) принимает подключения по HTTP. Телефон сам
  подключения не принимает — он ходит к другим. Всё, что пришло на узел, он передаёт дальше:
  событие с телефона, дошедшее до ПК, при следующей встрече ПК с сервером дойдёт и до сервера.
- **Подключение нового устройства.** На уже подключённом устройстве — «Подключить устройство»:
  код и QR с адресом и одноразовым ключом. Новое устройство вводит код и получает свой постоянный
  ключ к этому узлу. Связанные узлы образуют одну библиотеку.
- **Отзыв.** Отозванный узел больше не принимают; его события, уже попавшие в журнал, остаются.

## Приложения и связь

Решено 2026-11-04. Цель — лёгкая установка: человеку не нужно знать про Docker, порты, nginx.

- **Три приложения, один код.** Узлы одинаковые внутри, отличаются обёрткой:

| Приложение | Для кого | Как ставится | Особенность |
|---|---|---|---|
| **MUSICH для ПК** | все | установщик «Далее → Готово» | окно и значок в трее, сервер внутри |
| **MUSICH для телефона** | все | приложение Android | своя копия избранного, играет без связи |
| **MUSICH Сервер** | продвинутые | Docker на своём сервере, свой домен | без окна, всегда включён — посредник |

- **Без туннелей и сторонних посредников.** Никаких Tailscale, Cloudflare Tunnel и чужих серверов:
  устройства связываются только напрямую друг с другом или через свой MUSICH Сервер.
- **Дома — одна сеть Wi‑Fi.** ПК и телефон находят друг друга в локальной сети (`_musich._tcp`),
  подключаются по QR и синхронизируются по Wi‑Fi. Порты открывать не нужно. В интерфейсе —
  предупреждение: устройства видят друг друга, только когда они в одной сети Wi‑Fi; если другого
  устройства не видно — так и написать («не в одной сети»), а не молча ждать.
- **Свой сервер — по желанию, в настройках.** Раздел «Сервер» на ПК и телефоне: адрес
  (`https://домен`) и код подключения с самого сервера. После этого устройства синхронизируются
  через сервер откуда угодно, а дома — ещё и напрямую. Сервер — обычный узел, просто всегда включён.
- **Сервер наружу — забота продвинутого:** HTTPS на его стороне (для pi5 — плейбук ставит сайт nginx
  и сертификат). Внутри MUSICH: ограничение попыток входа, подключение устройств только по коду.

## Что синхронизируется

| Что | Ключ | Как устроено |
|---|---|---|
| Трек | id = отпечаток файла при первом появлении (как сейчас) | метаданные, текущий отпечаток файла, история отпечатков |
| Файл трека | отпечаток | передаётся отдельно от событий, по политике устройства |
| Правки трека в MUSICH | id трека + поле | по каждому полю отдельно: название, исполнитель, альбом, год, номер |
| Лайк | id трека | есть / нет |
| Плейлист | свой UUID (не имя) | название, описание, состав и порядок |
| Своя картинка | вид + ключ (трек, альбом, исполнитель, плейлист) | файл картинки передаётся как файл трека |
| История | id события | только добавляется |
| Корзина и удаление | id трека | метка «удалён из библиотеки», восстановление |
| Настройки библиотеки | ключ | разделители исполнителей, режим «Редактирование трека», правила имён файлов |
| Интеграции | сервис | снимок списка из Spotify, YouTube, Яндекса, VK |
| Решение конфликта | id конфликта | выбор человека |

**Не синхронизируется** — это свойства устройства: тема, шрифт, масштаб, колонки, эквалайзер,
громкость, очередь, папки с музыкой на этом устройстве, политика хранения файлов.

**Альбомы и исполнители** отдельными записями не синхронизируются — они собираются из тегов
и правок треков на каждом устройстве одинаково.

## Журнал событий

### Событие

```jsonc
{
  "id": "n7Kq…:1842",          // узел-автор : его порядковый номер, без пропусков
  "node": "n7Kq…",
  "n": 1842,
  "hlc": "2026-11-04T15:07:12.345Z/0003", // гибридные часы, см. ниже
  "type": "track.set",
  "key": "a1b2c3d4e5f6a7b8",   // о чём событие: id трека, UUID плейлиста, …
  "field": "title",            // для событий по полю
  "value": "Волна",
  "base": "Pz3x…:77"           // последнее событие по этому key+field, которое автор видел; null — не видел ни одного
}
```

Событие неизменно. Применяется один раз (по `id`); повторно пришедшее — пропускается.

### Типы событий

| type | key | Что значит |
|---|---|---|
| `track.add` | id трека | новый трек: отпечаток, размер, формат, длительность, исходные теги, имя файла, откуда пришёл |
| `track.file` | id трека | у трека новая версия файла (MUSICH записал теги в файл): новый отпечаток, предыдущий в `base` |
| `track.set` / `track.reset` | id трека, `field` | правка поля в MUSICH / вернуть как в файле; `autoGain` — измеренная громкость |
| `track.delete` / `track.restore` | id трека | удалить из библиотеки (в корзину) / вернуть |
| `track.purge` | id трека | окончательно стереть (корзина очистилась) |
| `like.set` | id трека | `value: true \| false` |
| `playlist.create` / `playlist.delete` | UUID | создать (название, описание) / удалить |
| `playlist.set` | UUID, `field` | `name`, `description`, `position` (место в списке плейлистов) |
| `playlist.add` | UUID | `value: { track, after }` — вставить трек после `after` (null — в начало) |
| `playlist.remove` | UUID | `value: { track }` |
| `playlist.move` | UUID | `value: { track, after }` |
| `cover.set` / `cover.clear` | вид:ключ | своя картинка: отпечаток файла картинки |
| `play` | id трека | прослушивание: когда, сколько, с какого устройства |
| `settings.set` | ключ настройки | значение |
| `integration.snapshot` | сервис | снимок списка сервиса целиком (последний побеждает) |
| `copy.have` / `copy.drop` | отпечаток | у узла-автора появилась / пропала копия файла |
| `conflict.resolve` | id конфликта | выбор человека |
| `node.add` / `node.revoke` | id узла | устройство подключено / отозвано |

### Гибридные часы (HLC)

Часы устройства могут врать, поэтому «когда» берётся не из них напрямую. Метка `hlc` =
физическое время + счётчик. При записи события метка = max(своё время, последняя известная
метка) + шаг; при получении чужих событий своя последняя метка подтягивается до самой большой
полученной. Так событие, сделанное после того, как устройство увидело другое, всегда «позже»
него, даже если в телефоне сбито время. При равных метках порядок решает `id` узла.

### Свёртка

Состояние = все события, применённые в порядке `hlc`. Для полей — побеждает событие с большей
меткой (если оно не в конфликте, см. ниже). Свёртка детерминирована: два устройства с одним и тем
же набором событий получают одну и ту же библиотеку и одни и те же конфликты.

## Обмен

- **Вектор** — для каждого известного узла последний номер `n`, который у меня есть:
  `{ "n7Kq…": 1842, "Pz3x…": 77 }`. Пропусков нет, поэтому вектор точно описывает, что у меня есть.
- **Встреча двух узлов.** Каждый отдаёт свой вектор, другой присылает события, которых нет
  (по каждому узлу — с номерами больше, чем в векторе), порциями. Затем то же в обратную сторону.
  Обрыв — не страшно: следующая встреча продолжит с нового вектора.
- **Файлы** качаются после событий, по политике устройства, по отпечатку, с докачкой (`Range`).
  Узел отдаёт файл, только если копия у него есть (`copy.have`).
- **Эндпоинты** (набросок, у узлов с HTTP):

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/sync/hello` | id узла, имя, тип, вектор |
| POST | `/api/sync/pull` | `{ vector, limit }` → `{ events, more }` — события, которых нет у спрашивающего |
| POST | `/api/sync/push` | `{ events }` → `{ vector }` — принять события |
| GET / HEAD | `/api/sync/file/:hash` | файл трека или картинки по отпечатку, с `Range` |
| POST | `/api/sync/pair` | `{ code, node, name, kind }` → `{ key }` — подключить устройство по коду |

- **Кто к кому ходит.** Телефон — к любому знакомому узлу, до которого достаёт (ПК дома по Wi‑Fi,
  свой сервер где угодно). ПК — к серверу, если он подключён. Адрес узла — найденный в локальной
  сети (`_musich._tcp`) или адрес своего сервера из настроек.

## Слияние и конфликты

**Одновременные изменения.** Два события об одном и том же (`key` + `field`) одновременны, если
ни одно не «видело» другое: у них одинаковый `base`, или `base` одного не ведёт к другому.
Только такие пары бывают конфликтом. Если автор видел прошлое изменение и поменял поверх — это
просто следующее изменение, никакого конфликта.

| Что | Обычное слияние | Конфликт, когда | Пока не решено | В «Конфликтах» |
|---|---|---|---|---|
| Новые треки | объединение | — | — | — |
| Правка поля | последняя метка | поле изменено по-разному одновременно | последняя метка | оба значения, выбрать |
| Вернуть как в файле против правки | последняя метка | одновременно | последняя метка | оба варианта |
| Версия файла (`track.file`) | последняя | две разные версии от одного `base` | главная — новая, старая хранится | какую оставить |
| Удаление против правки, лайка, добавления в плейлист | — | одновременно | трек остаётся | «удалить или оставить» |
| Лайк | последняя метка | — | — | — |
| Название плейлиста | последняя метка | — (молча) | — | — |
| Состав плейлиста | все добавления и удаления применяются | — | — | — |
| Удаление плейлиста против изменения | — | одновременно | плейлист остаётся | «удалить или оставить» |
| История | объединение | — | — | — |
| Настройка библиотеки | последняя метка | одновременно разные | последняя метка | оба значения |
| Одна песня из разных файлов (mp3 и flac) | два трека | не конфликт | — | в «Дубликатах»: слить |
| Удалённый трек снова прислали файлом | — | всегда | файл ждёт отдельно | «вернуть или стереть» (как сейчас) |

- **id конфликта** = отпечаток id участвующих событий. Каждое устройство находит одни и те же
  конфликты само, по журналу; передаётся только решение (`conflict.resolve`).
- **Решение — событие.** Решил на телефоне — решено везде. Решение остаётся в журнале.
- **Слить дубликаты** = выбрать главный трек: лайки, плейлисты, история и правки второго
  переходят к главному, второй уходит в корзину.

## Удаление

Два разных действия — и в интерфейсе, и в журнале:

| Действие | Что происходит | Событие |
|---|---|---|
| **Убрать с устройства** | стирается только файл здесь, трек остаётся в библиотеке, можно скачать обратно | `copy.drop` |
| **Удалить из библиотеки** | трек уходит в корзину на всех устройствах; файлы стираются, когда корзина очистится | `track.delete`, потом `track.purge` |

**Последняя копия.** По `copy.have` / `copy.drop` каждое устройство знает, где лежат копии файла.
Если копия здесь последняя, «убрать с устройства» не даётся: MUSICH предлагает сначала отправить
файл на другое устройство. Копии у отозванного узла не считаются.

## Файлы на устройстве

| Политика | Что держит | По умолчанию |
|---|---|---|
| Всё | все файлы библиотеки | ПК, сервер |
| Избранное | «Избранное», плейлисты с пометкой «держать на устройстве», добавленное на этом устройстве | телефон |
| По запросу | только то, что попросили | — |

Трек без файла на устройстве виден и играется потоком с узла, где файл есть (если тот доступен).

## Сжатие журнала

Событие, которое видели все неотозванные узлы, можно свернуть: узел хранит снимок состояния
и журнал после него. Новое устройство получает снимок и хвост. Узел, которого давно не видно,
сжатие задерживает — MUSICH показывает это и предлагает его отозвать.

## Переход с нынешней схемы

1. Сервер получает id узла и строит начальный журнал из своей базы: `track.add` и версии файлов
   по таблице `hashes`, правки (`tracks.ov`), лайки, плейлисты, картинки, история, корзина.
   Метки — по времени записей (`added_at`, `liked_at`, …).
2. Нынешние `GET /api/changes`, `musich-sync` и телефон продолжают работать, пока их не переведут.
3. Нынешние «Конфликты» (присланный удалённый трек, дубликаты) становятся частью общей страницы.

## Этапы

1. **Журнал на сервере.** ✅ Сделано 2026-11-04: начальный журнал из базы, каждое изменение сервера
   пишется событием, `/api/sync/hello`, `pull`, `file`. Приём событий (`push`) и подключение
   устройств (`pair`) — на следующих этапах. Подключение по коду на сервере сделано тогда же: `/sync/codes`,
   `/sync/pair`, «Подключить устройство» с QR и «Войти по коду» в веб-морде; плюс лимит попыток входа.
2. **Телефон пишет вверх всё.** Лайки, плейлисты, правки, удаления без сети — событиями.
3. **Телефон сам по себе.** Своя база, работает без сервера; подключение по коду и QR, поиск
   в локальной сети, предупреждение «нужна одна сеть Wi‑Fi». Поиск уже сделан (2026-11-04): сервер объявляет себя по mDNS
   (`server/src/discovery.ts`, на каждой сетевой карте со своим адресом), приложение ищет системным NsdManager
   (плагин `DiscoveryPlugin.java`), запасной путь — перебор подсети прошлого адреса; сервер узнаётся по `node`,
   сменился адрес — приложение само переезжает, не выходя из аккаунта и не теряя библиотеку.
4. **MUSICH для ПК** — позже и отдельно, когда доделана версия для сервера. Установщик, окно и значок в трее, синхронизация с телефоном и сервером на равных
   (`musich-sync` становится частью приложения); раздел «Сервер» в настройках.
5. **Конфликты везде.** Страница «Конфликты» на каждом устройстве, «Убрать с устройства» и защита
   последней копии.

## Как сделано (этап 1)

- **Миграция 17** (`server/src/db.ts`): таблица `events`, очередь `journal_pending` и триггеры на
  `tracks`, `likes`, `playlists`, `covers`, `plays`, `trash`, `settings`. Триггер кладёт сырое изменение
  (строка до и после), поэтому в журнал попадает всё: веб-морда, скан, слежка за папками, фоновые задачи.
- **`server/src/journal.ts`**: id узла (`settings.node`), гибридные часы, начальный журнал (`bootstrap`,
  один раз, отметка `settings.journal`) и `flush` — сырые изменения → события. `flush` зовётся после
  каждого запроса и раз в 2 секунды.
- **Что не пишется:** служебные поля (`seq`, `mtime`, путь на диске), пароль, токены, ключи сервисов,
  настройки узла (`rescanMinutes`, `watch`). Общие настройки — `playThreshold`, `trashDays`, `editMode`,
  `fileNames`, `autoNumber`, `shiftOnDelete`, `separators`, `dupIgnored`; снимки интеграций.
- **Папку убрали из библиотеки** (`unlinked`) — это не «удалить из библиотеки», а «у узла нет файла»:
  `copy.drop`. Вернули папку — `copy.have` (и `track.add`, если трек убрали ещё до журнала).
- **Правки «только в MUSICH»** уже лежат в колонках трека, поэтому в `track.file` поля, подменённые
  правкой, не попадают — только то, что на самом деле в файле.
